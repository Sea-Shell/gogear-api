# BR-020 — Containers nest to any depth, with one direct container per registration and no cycles

**Amendment of 2026-11-22 (anchor decision D11):** AC-1, AC-5, the statement, the terms and the verification now require that only registrations of container-capable gear ([BR-021](/docs/requirements/requirements/br-021-container-capability-from-category.md)) can hold other registrations. This supersedes provisional default P-11 ("any registration can act as a container"), which rested on a misreading of D9. **This amended part is implemented** in the container-capability change (see the implementation note below); the wave 7 code had let any registration hold any other.

**Implementation:** implemented in wave 7 (review mitigation); AC-1 and AC-5 as amended by D11 are implemented in the container-capability change (BR-021, migration 000009, [ADR-001](/docs/architecture/decisions/adr-001-category-driven-container-capability.md)): a link into a registration whose gear is not container-capable is 409 (message: this registration cannot hold items), decided after the 404 and the self-link 400 and before the other 409s, and the database repeats it with two triggers on link insert and update (tests `TestContainerCapability_*` in `pkg/api/container_capability_test.go`, `TestMigration9TriggersGuardLinkTargets`, and E2E-001). The wave 7 description below is otherwise unchanged; where it says that any registration can be a container, read AC-1 as amended (test `AnyRegistrationCanContainAnyOther` now states the D11 rule). `InsertContainer` runs in one immediate transaction: ownership of both registrations first (404), a self-link is 400 and checked before any 409, then a content that already has a container is 409 (AC-3), then a recursive walk up from the container that finds the content is 409 (AC-4, any depth). Nothing in the handlers reads `gearIsContainer`, so any registration can be container or content (AC-1, test `AnyRegistrationCanContainAnyOther`); the catalog flag stays only the `container` list filter. The database repeats the rules: migration 000008 adds a unique index on the content column (this supersedes the (container, content) unique index of 000005 and its redundant content index; a container-lookup index replaces them) and a cycle trigger on insert and update, so the concurrency guarantee (AC-6) also holds for a second connection. The same migration removes stored violations (AC-8): self-links, links with a missing container or content registration, links across owners, all but the oldest container of a registration, and one link per ring (the link that puts the ring's lowest-numbered member into its container). Deleting a registration still removes only its own links (AC-7). Adversarial tests: `pkg/api/container_nesting_test.go` (25-level chain, second container, indirect cycles of depth 2 to 5, precedence, concurrent A-into-B/B-into-A, three-way ring and X-into-C/X-into-D races, database-only enforcement, delete in the middle of a chain) and `migration8_test.go`. **Status:** Accepted with provisional conditions. **Priority:** P1 (review SEC-06 and section 9, data integrity). **Basis:** AC-1 (contents) and AC-2 are sourced from anchor decision D9. AC-1 (container role) is sourced from D11; its 409 status is a provisional default. AC-4 is derived from D9, because nothing can physically be inside itself. AC-3, AC-5 and AC-8 are provisional defaults or specified choices of the requirements author, marked where they apply. Ownership of every link stays as in [BR-013](/docs/requirements/requirements/br-013-container-links-owner-scoped.md).

**Terms:**
- *Container link*, *container*: as in [BR-013](/docs/requirements/requirements/br-013-container-links-owner-scoped.md). Here a container is any registration that holds, or is asked to hold, another registration. Only a registration of container-capable gear ([BR-021](/docs/requirements/requirements/br-021-container-capability-from-category.md)) can be given new contents.
- *Direct container* of X: the registration that a container link names as X's container.
- *Inside*: X is inside C if C is X's direct container, or X's direct container is inside C. This covers any depth.

**Statement:**
The API shall let a user put any of their own gear registrations into any other of their own registrations whose gear is container-capable, at any depth, as long as afterwards every registration has at most one direct container and no registration is inside itself.

**Acceptance criteria:**

- AC-1: A registration can receive new contents only while its gear is container-capable as defined in [BR-021](/docs/requirements/requirements/br-021-container-capability-from-category.md). Linking X into C when C's gear is not container-capable is refused with 409, the response says that C cannot hold items, and nothing changes. What a container holds is not restricted: any registration may be content, whatever its gear's classification, including a registration of container-capable gear and one that already holds other registrations. A registration that already holds contents when its gear stops being container-capable keeps them (BR-021 AC-6). Example: R1 is a backpack (container-capable) and R2 a tent bag (container-capable) holding R3; linking R2 into R1 succeeds. R4 is a headlamp (not container-capable); linking R3 into R4 is refused with 409. **[Sourced from D11. The 409 status is provisional default P-17 — open to product-owner change. Supersedes provisional default P-11.]**
- AC-2: There is no depth limit. Example: with R1 to R24 all registrations of container-capable gear, the owner links R2 into R1, R3 into R2, and so on, up to R25 into R24. Every link succeeds, and listing each container returns exactly its direct contents.
- AC-3: A registration has at most one direct container at a time. Linking X into C when X already has a different direct container D is refused with 409, and nothing changes. To move X, the owner removes the link to D and then links X into C. Linking X into C again when that link already exists stays a 409, as today. **[Provisional default P-12 — open to product-owner change]**
- AC-4: No registration is ever inside itself. Linking X into C is refused when C is X (400, as today) or when C is already inside X (409). Example: R2 is in R1 and R3 is in R2; linking R1 into R3 is refused with 409, and nothing changes. **[The 409 status is provisional default P-12]**
- AC-5: The ownership refusal of BR-013 (the "not found" outcome of [BR-018](/docs/requirements/requirements/br-018-denial-outcomes.md)) is decided before the 400 and 409 outcomes of AC-1, AC-3 and AC-4. Among those, the self-link 400 comes first, then the not-capable 409 of AC-1, then the 409s of AC-3 and AC-4. Example: linking X into a not-capable C while X already has a container returns the not-capable 409. A 400 or 409 response reveals nothing about another user's registrations or links. (Specified choice; it keeps BR-018's precedence.)
- AC-6: AC-3 and AC-4 hold when link requests run at the same time. Examples: concurrent requests "R1 into R2" and "R2 into R1" leave at most one of the two links stored; concurrent requests "X into C" and "X into D" leave X with at most one direct container. (Derived: otherwise two requests that are each valid alone could store a cycle or a second container.)
- AC-7: Deleting a registration removes only the links that involve it. Its direct contents stay in the owner's inventory with no direct container, and whatever they hold stays inside them. Removing a link changes no other link. (Specified choice; it matches today's behavior.)
- AC-8: Once this requirement is implemented, no stored link violates AC-3 or AC-4, and no stored link joins registrations of different owners. This includes self-links and multiple direct containers stored before. How existing violations are removed is a realization choice. Removing such links is allowed, because the product owner stated that the stored data is generated test data, so no existing link needs to be preserved. (Specified choice, enabled by the anchor's context note.) A stored link whose container's gear is not, or no longer, container-capable is not a violation and stays (BR-021 AC-6).

**Out of scope:** whether contents physically fit, for example against a registration's maximum container weight. The product owner has not decided this, and no limit is required.

**Verification semantics:**
Use real request handling and stored data. Build the 25-level chain of AC-2. Try to link a registration that already has a container into a second container: 409, and both stored links are unchanged. Try the cycle of AC-4, and a cycle of length 2: 409, no link added. Try a self-link: 400. Run the two concurrent pairs of AC-6 many times: never two links stored. Delete a middle registration of the chain: its child has no container, and the rest of the chain below it is intact. Link into a registration whose gear is not container-capable: 409 with the not-capable message, no link added, also when the content already has a container (AC-5 order). Link a registration of non-container gear, and one of container-capable gear, into a container: both succeed. After the change, check the stored links for self-links, multiple direct containers, cycles and cross-owner links: finding any falsifies AC-8. The requirement is falsified by any stored state where a registration has two direct containers or is inside itself.
