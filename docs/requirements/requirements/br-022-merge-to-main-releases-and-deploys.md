# BR-022 — A merge to main releases and deploys a new version with no manual step

**Implementation:** implemented and verified. `release.yaml` now calls the nrkno semantic-release workflow v5.1.6 (`a68fb147`), guards build and deploy on `released == 'true'`, serializes runs in a non-cancelling concurrency group, and ends with a "Verify deployed pod" step (ADR-002). The app prints `gogear-api migrations: version=<N> dirty=<bool>` to stdout after every successful migration run, including when nothing changed and whatever the log level (AC-7 (e) evidence). Verified 2026-11-22 by [run 45061018365](https://github.com/Sea-Shell/gogear-api/actions/runs/45061018365) (push-triggered, attempt 1, green; Loom QA record 1add5a2a). AC-1 and AC-2: the run released `v4.9.6` (annotated tag and GitHub release), built it, pushed digest `sha256:23bf66e722464188a36c136bca269d6923ac9262c6371497e92fa44ec11bf378`, connected Tailscale and completed the rollout, with no human step. AC-7 per part: (a) the push-triggered run was green on its first attempt; (b) tag `v4.9.6` and its GitHub release exist; (c) the pushed digest is the one the deploy used (checks I-1 and I-2 passed, and I-4 reported that the `imageID` digest equals the build digest); (d) the rollout completed (R-1), one live pod (P-1) runs the image (I-2, I-3) and is healthy with no restarts after the wait (H-1); (e) the deployed pod logged `gogear-api migrations: version=10 dirty=false` (M-1), the highest migration in the tag. Earlier proof runs failed and were fixed: [45027087596](https://github.com/Sea-Shell/gogear-api/actions/runs/45027087596) (`v4.9.4`, missing `pods/log` permission, fixed by the owner) and [45048563144](https://github.com/Sea-Shell/gogear-api/actions/runs/45048563144) (`v4.9.5`, `imageID` digest gate, fixed by ADR-002 D-11 in #485). AC-3 (no release, no tag, build or deploy, run still green) is verified in production by [run 45063049018](https://github.com/Sea-Shell/gogear-api/actions/runs/45063049018), triggered by the push of #486's squash commit `876965f`: the release job logged "no release: no bump-worthy commits", the build and deploy jobs were skipped, the run is green, and no tag or release exists after `v4.9.6`. Not yet shown in production: the "differs" branch of check I-4. Before this change, on `main` at `a8526c3`, the release workflow had not produced a release since 2026-06-24 (anchor RD1 context). **Status:** Accepted. **Priority:** P0 (no merged change reaches the server until this holds). **Basis:** the statement and AC-1 come from anchor decision [RD1](/docs/anchors/release-and-deployment.md) ("no manual steps when deploying a new version"; "deployed by workflow … tailscale … kubernetes"). AC-2 (what "manual" means) and AC-7 (evidence) are derived: without them "no manual step" cannot be checked. AC-5 (version order) is derived: a release that computes a lower version than the last one would not be "a new version". AC-6 (pinning) preserves an accepted repository policy, as the brief requires. AC-3, AC-4 and AC-8 are specified choices of the requirements author, marked where they apply.

**Terms:**
- *Merge to main*: any change that lands on the `main` branch of the repository (a merged pull request or a direct push).
- *Release-worthy change*: a change whose commits, under the release rules, call for a new version. Which commit types are release-worthy, and which version part each one bumps, is an open technical choice for the architect (see "Open technical choice").
- *Release*: the new version tag in the repository and its GitHub release.
- *Deploy*: the new image running in the owner's Kubernetes server, reached through the existing Tailscale connection and Kubernetes setup.
- *Release run*: one run of the repository's release workflow on `main`.
- *Manual step*: any action a person takes, after the merge, that the release or deploy of that merge needs. Examples: dispatching or re-running a workflow or job, approving a run or an environment, creating or moving a tag, building or pushing an image by hand, running `kubectl` or applying manifests, editing a secret, variable or server setting for this release, or changing data in the API so the new version works. **Not a manual step:** one-time repository, secret and server setup that already existed before the merge and is not changed for the release (for example the Docker Hub, kubeconfig and Tailscale secrets, branch protection and the cluster itself); merging the pull request; and read-only observation of the result.

**Statement:**
When a release-worthy change is merged to main, the repository's release workflow shall, in one release run triggered by that merge and with no manual step, create a new version, build and push its image, and deploy that image to the owner's Kubernetes server.

**Acceptance criteria:**

- AC-1 (normal path): After a merge to main that contains a release-worthy change, exactly one release run starts because of the merge. That run, without any manual step, (a) creates a new version tag and its GitHub release, (b) builds an image from the tagged commit and pushes it under that version tag, and (c) deploys that image, identified by its pushed digest, to the owner's Kubernetes server. The run ends successfully only if all three happened.
- AC-2 (no manual step): No manual step (Terms) is needed for AC-1. A release counts as meeting this requirement only if its release run started from the merge itself and finished successfully on its first attempt. A run that a person started, re-ran, approved or completed by hand does not count, even if the result is the same.
- AC-3 (no release-worthy change): After a merge to main that contains no release-worthy change, the release run creates no tag and no GitHub release, builds and pushes no image, and deploys nothing; the server keeps running the version it had. The run still ends successfully. **[Specified choice: a skipped release is a normal outcome, not a failure, so a failed run always means something is wrong.]**
- AC-4 (failure is visible): If any part of AC-1 fails, or the version tag the run produces is missing or empty, the release run ends as failed; it never ends successfully after a partial release. A run deploys only the image it pushed itself, under its own version tag. A version tag may exist without a deploy only when the run that created it failed. This requirement does not promise an automatic retry or rollback; the next release-worthy merge must still release and deploy as in AC-1. **[Specified choice]**
- AC-5 (version order): Each new version is higher than every version already released in the repository, which on `main` at `a8526c3` is `v4.9.3`. A release run never re-creates or moves an existing version tag.
- AC-6 (pinning policy stays): The repository's strict pinning policy stays in force: every action and reusable workflow the release run uses, directly or through another workflow or action, is referenced by a full 40-character commit SHA. Meeting this requirement by turning that policy off, relaxing it, or exempting the release workflow from it falsifies it.
- AC-7 (evidence): A release meets this requirement when all of the following are observed for one merge: (a) one release run on `main`, triggered by the push of the merge, with every job successful and no human-triggered run or re-run for that merge; (b) the new version tag and its GitHub release exist; (c) the image with that version tag exists in the registry, and its digest is the digest the deploy used; (d) the rollout in the owner's Kubernetes server completed, and the API pod runs that image and is still running without restarts a few minutes after the rollout; (e) the deployed API's database is at the highest migration version contained in the released commit. Evidence (d) and (e) may come from the run's logs or from a read-only check by the owner; such a check is evidence collection, not a manual step.
- AC-8 (merges close together): When several merges reach main before earlier release runs have finished, every release-worthy change is released in some successful release run (one release may include several merges), and once all those runs have finished the server runs the highest released version, never an older one. **[Specified choice]**

**Out of scope:** what the release notes say; whether floating tags such as `v4` or `v4.9` are kept up to date; deployment to any server other than the owner's Kubernetes server; how the release, build and deploy are structured (one workflow or several jobs, which actions, which configuration). Rollback to an earlier version is not required here.

**Technical choice (decided by ADR-002 D-3; the run that released `v4.9.6` applied it and run 45063049018 applied it to a `docs:` change that released nothing; the `feat` and breaking rules are not yet exercised in production):** the upstream default rules of nrkno v5.1.6 apply: breaking → major, `feat` → minor, `fix` → patch, other types release nothing. They match the past behaviour of this repository, except that `perf` and `revert` no longer release (none exist in history). The bump comes from all unreleased commits since the last tag. Originally left open to the architect, who was to keep the earlier release behavior of this repository where it is known (releases until `v4.9.3`, made with the previous release workflow). If no earlier behavior can be established and the choice changes what reaches the server (for example whether dependency-update chores deploy), raise it to the owner through General. Until then, the requirement only demands that the rule is applied the same way every time and that AC-3 holds for commits it does not count.

**Verification semantics:**
Before the merge: show from a non-publishing rehearsal that the release step would compute a version higher than `v4.9.3` (AC-5), and that with no release-worthy commit it computes `released=false` and the build and deploy are skipped (AC-3). A semantic-release dry run reports `released=false` even when it computes a tag (`released = !dryRun`), so it proves only the computed `tag`; `released=true` is shown only by a local non-dry run against a bare repository and a stub GitHub API; scan every `uses:` reference in the release path, including nested workflows and actions, for full SHAs (AC-6). These checks are necessary but do not prove the requirement. After the merge: collect AC-7 (a) to (e) for the merge's release run. The requirement is falsified by any of: no run started by the merge; a run that needed any manual step, including a re-run; a successful run without a new tag, pushed image or completed rollout; a deployed digest that differs from the pushed one; a pod that restarts or a database below the released migration version; a version not higher than the previous one; a tag, image or deploy from a merge with no release-worthy change, or a failed run for such a merge; or any action or reusable workflow in the release path not pinned to a full SHA.
