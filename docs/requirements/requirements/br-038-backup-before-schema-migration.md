# BR-038 — The application backs up its database before it applies schema migrations

**Implementation:** implemented 2026-11-22 as task A6b of milestone A, on branch `loadout-loop-support`, in the same PR as migration 000011: package `pkg/dbupgrade` (tests in `pkg/dbupgrade/dbupgrade_test.go`, `startup_test.go`, `config_validation_test.go`), per [ADR-006](/docs/architecture/decisions/adr-006-pre-migration-backup-and-restore.md) and [ARS-002](/docs/architecture/spec/ars-002-pre-migration-backup-and-restore.md). The defaults of AC-8 (refuse) and AC-10 (keep and report) are two constants in `pkg/dbupgrade/policy.go` until Q-8 and Q-9 are answered. The README section "Automatic backup before schema migrations, and restore" describes it; the manual methods stay as an extra. **Status:** Accepted with provisional conditions. **Priority:** P0. **Deadline:** it must be in effect no later than migration 000011, so it is a precondition for merging milestone A of loadout planning (BR-023 to BR-025, BR-030, BR-036). The first production start that applies 000011 must already make the backup. **Basis:** the statement, AC-1 and AC-7 are sourced from anchor decision [RD3](/docs/anchors/release-and-deployment.md) (the application handles the backup and its upgrades itself, without relying on the user), read together with RD1 (no manual step). AC-2 is derived: a backup that misses or tears data does not protect the upgrade. AC-4 and AC-5 are derived from RD3 and RD1. AC-3 (location), AC-6 (retention), AC-8 (failure) and AC-9 (restore details) are provisional defaults P-37 to P-40, marked where they apply. AC-10 and AC-11 are specified choices.

**Terms:**
- *Pending migration*: a schema migration that this application version contains and the database has not applied yet.
- *Pre-migration backup*: the copy of the database this requirement makes before pending migrations are applied.
- *Persistent storage*: storage that keeps its content when the application restarts, its pod is replaced, or a new version is deployed. In the owner's deployment this is the `hostPath` volume that already holds the configuration and the database.

**Statement:**
Before the application applies any pending schema migration at startup, it shall automatically make a consistent backup of the database on persistent storage, with no step by the owner or anyone else. The owner shall be able to restore such a backup without copying database files by hand.

**Acceptance criteria:**

- AC-1 (when): Each time the application starts and finds at least one pending migration, it makes one pre-migration backup before the first pending migration changes anything. Nobody has to start, approve or trigger it. This holds on every release path, including the zero-touch release of [BR-022](/docs/requirements/requirements/br-022-merge-to-main-releases-and-deploys.md), and for every release with a pending migration, starting with the one that brings migration 000011.
- AC-2 (consistent): A pre-migration backup holds exactly the committed content of the database at one moment, the moment just before the migration starts. This includes changes that are only in the write-ahead log so far. It has nothing half-written and nothing from after that moment. No write can be committed between the moment of the backup and the start of the migration, so no data written before the upgrade is missing from the backup. The backup is a complete database on its own: it opens as a SQLite database, passes SQLite's integrity check, and reports the schema version the database had before the migration. The application checks this before it starts the migration; a backup that fails the check counts as a failed backup (AC-8). (Derived: otherwise the backup cannot undo the upgrade.)
- AC-3 (where): Backups are stored on persistent storage that the application itself can reach. By default this is a dedicated backup directory on the same volume as the database, never the database file's own name or the files SQLite uses next to it. The location can be changed in the application's configuration. Backups are never served over the API, and they get the same access protection on disk as the database file. Each backup is identified by the time it was made, the schema version it holds, and the application version that made it. The application reports each backup it makes (its location and that identity) on its standard output, in the same way as the migration version line of BR-022 AC-7, so the owner sees it in the pod log without opening the volume. **[Location and default: provisional default P-37 — open to product-owner change]**
- AC-4 (nothing pending): When no migration is pending, the application makes no backup and starts exactly as before. No new file appears.
- AC-5 (first start): When the database does not exist yet (the first start on an empty volume), there is nothing to protect, and no backup is made.
- AC-6 (retention): The application keeps the three most recent pre-migration backups and removes older ones automatically, so storage does not grow without bound. It removes an older backup only after a new backup has passed the check of AC-2. It never removes files it did not create. Example: backups exist from versions 9, 10 and 11; the release with migration 12 makes a fourth backup, checks it, then removes the version-9 backup. **[Three backups: provisional default P-38 — open to product-owner change]**
- AC-7 (no user step): Neither the backup nor the retention needs any step by a person: no script, no manual copy, no access to the node, no stopping of the service by hand. One-time setup that already exists (the volume, the deployment) is not a manual step (BR-022 terms).
- AC-8 (backup fails): If the pre-migration backup cannot be made or fails the check of AC-2 (for example, the disk is full), the application applies no migration and leaves the database unchanged. It does not start serving requests, and it reports the reason on its standard output and log. Any partial backup file is removed or clearly marked as not valid, and it never counts towards AC-6. Because the service then does not start, the release run of BR-022 fails visibly (BR-022 AC-4); nothing fails silently. Once the cause is fixed, the next start makes the backup and migrates as normal, with no other step. **[Refuse to migrate: provisional default P-39. The alternative for the owner, migrating without a backup and warning, is open question Q-8.]**
- AC-9 (restore): The owner can put the database back to the state of any kept backup without copying database files by hand and without shell access to the node, using means the deployment already offers (for example the release workflow, a Kubernetes action, or the application's configuration). Restoring happens while the application serves no requests. It replaces the current database as a whole, never partly. The database being replaced is itself kept as a backup first, so a restore can be undone. After a restore, the application reports the restored backup's identity and the schema version now in effect. If the restored schema version is older than the running application expects, that application's next start migrates it again under this requirement, with a new backup. To return to an older release, the owner restores that release's backup and deploys the older version; the backup's identity (AC-3) says which version that is. How restore is triggered is a realization choice, and it must be documented in the README. **[Provisional default P-40 — open to product-owner change]**
- AC-10 (migration fails after a good backup): If a migration fails after the backup was made, the backup stays and is not removed by retention. The application reports which backup holds the state from before the attempt. Whether it should also restore that backup automatically is open question Q-9; until it is answered, it does not. (Specified choice.)
- AC-11 (engine scope): This requirement applies to the SQLite database the application runs on today. A database hosted outside the application is not supported now, and no requirement is written for one. If one is introduced, RD3's principle applies: the application stays responsible for the safety of its own upgrades, and the requirement must be written for that engine then.

**Out of scope:** copies on other disks or off the server (a backup on the same volume does not protect against losing that disk); scheduled backups unrelated to migrations; encryption of backups.

**Verification semantics:**
Use the real application start-up against real database files. Seed a database at version 10, with data, and with writes that are still only in the write-ahead log; start a version that contains migration 11. A backup appears in the configured location before the schema changes. It opens, passes the integrity check, reports version 10, and contains every seeded row, including the logged writes. The stdout line names it. Start again with nothing pending: no new backup. Start on an empty volume: no backup. Run four upgrades in a row: three backups remain, and the oldest went only after the new one was checked. Make the backup fail (full disk, unwritable directory): the database is unchanged at version 10, no migration ran, the service is not ready, the reason is logged, no partial backup counts, and after fixing the cause a plain restart succeeds. Restore a kept backup through the documented means: the database equals that backup, the replaced database is kept as a backup, and no file was copied by hand. Make a migration fail after the backup: the backup remains and is reported. Any migration that runs without a checked backup before it, under the default of AC-8, falsifies the requirement.
