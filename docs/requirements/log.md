# Requirements change log

## 2026-11-22

- **Status change:** [BR-022](/docs/requirements/requirements/br-022-merge-to-main-releases-and-deploys.md) AC-3 (no-release path) is now verified in production. [run 45063049018](https://github.com/Sea-Shell/gogear-api/actions/runs/45063049018), triggered by the push of #486's squash commit `876965f` (a `docs:` change): the release job logged "no release: no bump-worthy commits", the build and deploy jobs were skipped, the run is green, and no tag or release exists after `v4.9.6` (run 45063049018). Requirement text is unchanged. [Index](/docs/requirements/index.md) updated.
- **Status change:** [BR-021](/docs/requirements/requirements/br-021-container-capability-from-category.md) AC-5 seeding is now verified in production. Verified in production 2026-11-22: the owner ran a read-only query on the production database after the `v4.9.6` deploy (migration version 10) and found these sub-categories with `categoryIsContainer = 1`: 16 Hiking backpack, 17 Daypack, 18 Hydration backpack and 19 Water bottle. Water bottle was seeded because at least one of its gear items carried the legacy per-gear flag, which is exactly what P-18 specifies; an admin can change it with `category_container: "not_container"`, and no requirement change is needed. Requirement text is unchanged. [Index](/docs/requirements/index.md) updated.
- **Status change:** [BR-022](/docs/requirements/requirements/br-022-merge-to-main-releases-and-deploys.md) is now implemented and verified. [run 45061018365](https://github.com/Sea-Shell/gogear-api/actions/runs/45061018365) (push-triggered, attempt 1, green; Loom QA record 1add5a2a) released `v4.9.6` (annotated tag and GitHub release), pushed digest `sha256:23bf66e7…f378`, connected Tailscale, completed the rollout and passed R-1, I-1, P-1, I-2, I-3, H-1, I-4 ("equals") and M-1 (`version=10 dirty=false`). The BR-022 entry records the evidence per AC-7 part, and the earlier failed proof runs 45027087596 and 45048563144. Requirement text is unchanged. AC-3 (no-release run) was not yet shown at that point (see the next entry). [BR-021](/docs/requirements/requirements/br-021-container-capability-from-category.md) AC-5 seeding was not yet marked verified in production at that point (see the next entry). [Index](/docs/requirements/index.md) updated.

- **Amendment:** The product owner stated that deploying a new version must need no manual step, and that the existing workflow deploys to their Kubernetes server through Tailscale ([anchor decisions RD1 and RD2](/docs/anchors/release-and-deployment.md)). Requirement text changed; nothing of it is implemented yet:
  - New [BR-022](/docs/requirements/requirements/br-022-merge-to-main-releases-and-deploys.md): a merge to `main` with a release-worthy change tags, builds and pushes the image and deploys it in one push-triggered run with no manual step. Defines manual steps (one-time existing setup is not one; a dispatch, re-run, approval or any per-release action is), the no-release case (no tag, build or deploy, run still green), the evidence (green run through deploy, pushed digest deployed, pod still running, database at the latest migration), version order above `v4.9.3`, and that full-SHA action pinning stays in force. Which commit types are release-worthy is open technical choice T-1 for the architect.
  - [BR-021](/docs/requirements/requirements/br-021-container-capability-from-category.md) AC-5 amended: container settings are seeded from the old per-gear flags in the release itself (a sub-category with any flagged gear becomes explicitly a container category; top categories stay not container categories). **P-14 is superseded** (it needed admins to mark categories after deploy); the old text is kept struck through. New provisional default P-18. Implementation note, deployment note, basis and verification updated; the amended AC-5 is not implemented.
  - [Index](/docs/requirements/index.md): release summary, BR-021 and BR-022 rows, P-14 marked superseded, P-18 added, T-1 added, implementation-status notes updated.

- **Amendment:** The product owner stated that the category or sub-category, not the gear item, decides whether something is a container ([anchor decision D11](/docs/anchors/access-control-and-identity.md); detailed rules adopted on General's proposal, open to owner change). Requirement text changed; nothing of it is implemented yet:
  - New [BR-021](/docs/requirements/requirements/br-021-container-capability-from-category.md): admins set container capability on top categories and sub-categories; a sub-category inherits its top category's setting unless it has its own; gear container status is derived from its sub-category. Provisional defaults P-13 to P-16.
  - [BR-020](/docs/requirements/requirements/br-020-container-nesting-consistency.md): AC-1 now allows new contents only in registrations of container-capable gear (409 otherwise, P-17); AC-5 orders that 409 after the self-link 400 and before the other 409s; statement, terms, AC-2 example, AC-8 and verification updated. **P-11 is superseded**: it read D9 as "anything can be a container", which the owner says was a misunderstanding.
  - [BR-001](/docs/requirements/requirements/br-001-catalog-changes-admin-only.md): new AC-6, the container settings are admin-only catalog data.
  - [BR-013](/docs/requirements/requirements/br-013-container-links-owner-scoped.md): terms point to BR-021.
  - [Index](/docs/requirements/index.md): BR-021 row, terms, P-11 marked superseded, P-13 to P-17 added, Q-4 and wave 7 notes updated.
